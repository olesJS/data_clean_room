# Словник даних і структура картки набору (Data Dictionary)

Документ описує, які метадані показує каталог Data Clean Room (UC-12) і що саме лежить у колонках очищених демонстраційних наборів `payroll.csv` та `customers.json`. Це аспект «Метадані та каталог даних» з розділу 8 [data-governance-requirements.md](data-governance-requirements.md) (пріоритет: середній).

> **Статус документа.** Анонімізація (`backend/app/services/anonymizer.py`) уже в `main`, тому значення «стало» в розділі 2 отримані запуском цього коду на файлах `data/payroll.csv` і `data/customers.json`. Розділи 1 і 3 поділені на **«є зараз»** (те, що віддають модель, API і `/api/catalog` у `main`) та **«ціль UC-12»** (те, чого поки немає). Кількості рядків після очищення (484 / 950) — **цільові**, а не поточні: див. розділ 2.

## 1. Структура картки набору

Колонка «Хто заповнює»: **Система** — обчислюється автоматично при завантаженні, профілюванні, публікації; **Provider** — вводить власник набору.

### 1.1. Є зараз

**Каталог для Consumer (`GET /api/catalog`).** Віддає лише опубліковані набори (`status = published`) і лише такі поля:

| Поле | Тип | Опис | Хто заповнює | Приклад |
| --- | --- | --- | --- | --- |
| `id` | ціле | Ідентифікатор набору | Система | 1 |
| `name` | рядок | Назва набору | Provider | payroll |
| `data_class` | enum: Internal / Confidential / Personal | Клас за governance 3.1; після публікації перераховується шлюзом (SCRUM-57) за застосованими методами | Система | Personal |
| `row_count` | ціле | Кількість рядків **вихідного** набору (не очищеної версії) | Система | 500 |
| `quality_score` | число 0–100 | Оцінка якості за правилами YAML (UC-03/04) | Система | 91.8 |
| `anonymization_methods` | перелік {column, method} | Метод для кожної PII-колонки: `mask` / `generalize` / `hmac` | Provider обирає, система застосовує | `ipn` → `hmac` |
| `uploaded_by` | рядок (email) | Власник — Provider, що завантажив набір | Система (з облікового запису) | provider@example.com |
| `created_at` | дата-час (UTC) | Момент завантаження | Система | 2026-10-24T09:15:00 |

**Модель `Dataset` і API для Provider/Steward** додатково мають: `original_filename`, `file_type` (csv/json), `file_size`, `columns` ({колонка: тип}), `profile_json`, `pii_json`, `status` (`uploaded` / `published`), `retention_until` (дата, не раніше за сьогодні для публікації, SCRUM-57), `published_at`, `published_by`. **Правова підстава** (`LegalBasis`) зберігається окремо: тип `consent` / `contract` / `law`, мета `purpose` (`analytics` / `research` / `reporting` / `publication`), `valid_until` (необов'язкова дата), відкликання (UC-14).

**Видимість за ролями (governance 3.2).** Consumer бачить лише метадані очищеної версії опублікованого набору. Профіль (`profile_json`), PII-колонки з маскованими прикладами (`pii_json`) і дані сирого файлу Consumer не отримує (запит профілю повертає 403). Provider (власник) бачить метадані обох версій. Data Steward бачить метадані, профіль (`profile_json`), PII-колонки з маскованими прикладами (`pii_json`) та журнал аудиту, але не вміст наборів.

### 1.2. Ціль UC-12 (поки немає)

Це поля, яких немає в моделі, або які `/api/catalog` не віддає. Їх треба додати в API і UI, щоб картка відповідала UC-12.

| Поле | Опис | Хто заповнює | Приклад | Чого бракує |
| --- | --- | --- | --- | --- |
| Опис | Короткий зміст і призначення набору | Provider | Виплати працівникам за 2026 р. для зовнішнього аудиту | Немає в моделі `Dataset` і API |
| Семантика колонки | Зміст кожної колонки словами (розділ 2); показується поруч із типом | Provider (підказку може пропонувати система) | «ІПН працівника» | Немає в моделі `Dataset` і API |
| Колонки з типами | Перелік колонок очищеної версії | Система | `amount_uah: float` | `columns` є в моделі, але `/api/catalog` його не віддає |
| Правова підстава: тип, мета, чинність, статус | `contract`, `reporting`, до 2027-12-31, чинна/відкликана/прострочена | Provider; статус — система | `contract` / `reporting` | Є в `LegalBasis`, але картка каталогу не показує |
| Термін зберігання | Після `retention_until` набір підлягає видаленню (governance 3.6, UC-13) | Provider | 2027-12-31 | Є в `Dataset`, але `/api/catalog` не віддає |
| Статус публікації, `published_at` | Для Consumer лише `published` | Система | `published` | Не входить у картку каталогу |

Правила узгодженості картки (діють і для цілі):

1. Опублікувати набір неможливо, поки не заповнені: метод для кожної PII-колонки, чинна правова підстава для HMAC-колонок і `retention_until` (governance 3.5). Публікацію також блокують порушення якості з дією `block` (`quality_blocked`, SCRUM-57).
2. Клас знижується до Confidential тільки якщо **всі** PII-колонки маскуються або узагальнюються. HMAC є псевдонімізацією, тому клас лишається Personal.
3. Після відкликання правової підстави (UC-14) нові схвалення й завантаження блокуються, а вже передані дані лишаються в журналі аудиту.

## 2. Словник колонок очищених версій

Позначки методів відповідають `anonymizer.py`: **mask** — маскування `mask_val`, **generalize** — узагальнення `generalize_val`, **hmac** — HMAC-SHA256 `hmac_sha256_val`, **—** — колонка не змінюється. «Була PII» — результат PII-детектора на вихідному наборі. Приклади «стало» отримано запуском `apply_anonymization` на реальних даних; набір методів по колонках — демонстраційна конфігурація.

Правила маскування `mask_val` (порядок перевірки):

1. Є `@` → email: перша літера імені + `***` + `@` + перша літера домену + `***.` + остання частина після останньої крапки (`d***@i***.com`). Домен **теж маскується**. Без крапки в домені — `перша літера***`; порожній домен — `***`.
2. Починається з `+` (або з `0` і має 10 цифр) → телефон: перші 4 символи + `*****` + останні 2 (`+380*****63`).
3. Довжина ≥ 8 і є цифра → ІПН / IBAN / картка: `******` + останні 4 символи.
4. Інший рядок: перша літера + `***` + остання літера (для довжини ≤ 2 — `**`). Тобто для ПІБ маскується **весь рядок, а не кожне слово**.

> **Важливо про кількості рядків.** У таблицях нижче «очищена версія» — це **цільова** поведінка за UC-04/UC-06, коли рядки з дією `reject` відкидаються (500 → 484 і 1000 → 950). **Поточна реалізація їх не відкидає**: очищена версія містить усі 500 / 1000 рядків (розбіжність №3 у `docs/testing/test-cases-uc06-uc10.md`). Тестувальнику не слід брати 484 / 950 як еталон, доки розбіжність не закрита. Правила `flag` рядки не видаляють у жодному випадку.

### 2.1. `payroll.csv` (кейс 1: HR → зовнішній аудитор)

Вихідний набір: 500 рядків. Правила (`data/payroll_rules.yaml`): `amount_uah > 0` (reject), `payment_date <= today` (reject), `ipn` не порожній (flag). Рядків 500 зараз → **484 ціль** (16 reject-рядків). У очищеній версії лишаються **15 порожніх `ipn`** (порожнє значення HMAC не хешує) і **10 дублікатів `employee_id`**. Quality Score вихідного набору — 91.8.

| Колонка | Тип | Семантика | Була PII | Метод | Формат після обробки | Приклад (було → стало) |
| --- | --- | --- | --- | --- | --- | --- |
| `employee_id` | рядок | Табельний номер працівника | ні | — | `E` + 5 цифр; **не гарантовано унікальний** (10 дублікатів) | E00453 → E00453 |
| `full_name` | рядок | ПІБ працівника | так (person_name) | mask | Перша літера + `***` + остання літера всього рядка | Руденко Тарас Тарасович → Р\*\*\*ч |
| `ipn` | рядок | Реєстраційний номер облікової картки платника податків | так (ipn) | hmac | 64 hex-символи (SHA-256); однакові ІПН дають однаковий хеш, залежить від ключа `HMAC_KEY`. **15 порожніх значень лишаються порожніми** | 2663272534 → 3577c360…8048d13 (з тестовим ключем) |
| `iban` | рядок | Рахунок отримувача виплати | так (iban) | mask | `******` + останні 4 символи | UA883644124840841495022491758 → \*\*\*\*\*\*1758 |
| `position` | рядок | Посада | ні | — | Одне з 11 довідникових значень | Юрист → Юрист |
| `department` | рядок | Підрозділ | ні | — | Одне з 7 довідникових значень | Юридичний відділ → Юридичний відділ |
| `amount_uah` | число (2 знаки) | Сума виплати, грн | ні | — | Дійсне число; > 0 гарантується лише після відкидання reject-рядків (ціль) | 52574.65 → 52574.65 |
| `payment_date` | дата | Дата виплати | ні | — | `YYYY-MM-DD`; не пізніше за дату обробки гарантується лише після відкидання reject-рядків (ціль) | 2026-01-21 → 2026-01-21 |

Клас очищеної версії: **Personal** (колонка `ipn` псевдонімізована HMAC). Щоб знизити клас до Confidential, замініть метод для `ipn` на `mask` (`******2534`); тоді аудитор втрачає можливість зв'язувати виплати за ІПН. Мета правової підстави для цього кейсу — `reporting`.

### 2.2. `customers.json` (кейс 2: ритейл → рекламне агентство)

Вихідний набір: 1000 записів. Правила (`data/customers_rules.yaml`): `age` у межах 0–120 (reject), `registration_date <= today` (reject), `email` валідний формат (flag), `city` не порожнє (flag). Записів 1000 зараз → **950 ціль** (50 reject-записів). У очищеній версії лишаються **15 дублікатів `customer_id`**, **40 порожніх `city`** і **22 записи з невалідним `email`**. Quality Score вихідного набору — 87.0.

| Колонка | Тип | Семантика | Була PII | Метод | Формат після обробки | Приклад (було → стало) |
| --- | --- | --- | --- | --- | --- | --- |
| `customer_id` | ціле | Внутрішній ідентифікатор клієнта | ні | — | 6-значне; **не гарантовано унікальне** (15 дублікатів) | 100001 → 100001 |
| `full_name` | рядок | Ім'я та прізвище клієнта | так (person_name) | mask | Перша літера + `***` + остання літера всього рядка | Дмитро Маслюк → Д\*\*\*к |
| `email` | рядок | Електронна пошта | так (email) | mask | `x***@y***.zzz`: домен теж маскується. Невалідні адреси маскуються за тими самими правилами | dmytro.maslyuk217@icloud.com → d\*\*\*@i\*\*\*.com |

## 3. Зв'язок з UC-12 і каталогом у UI

### 3.1. Є зараз

- Каталог для Consumer (`GET /api/catalog`) показує поля з розділу 1.1: назву, клас, кількість рядків, Quality Score, методи анонімізації, власника, дату створення. Список колонок, правову підставу, `retention_until` і опис картка не показує.
- Дані беруться з `Dataset` (назва, клас, рядки, Quality Score, статус, `retention_until`), `AnonymizationMethod` (методи по колонках) і `LegalBasis` (окремий реєстр).
- Профіль (`profile_json`) і PII-приклади (`pii_json`) недоступні Consumer; їх бачать Provider і Steward.
- Словник колонок (розділ 2) — еталон для перевірки очищених файлів і PII-детектора в тест-кейсах.

### 3.2. Ціль UC-12

- Картка набору показує всі поля розділу 1.2: опис, колонки з типами й семантикою, правову підставу (тип, мета, чинність, статус), `retention_until`, статус публікації. Для Consumer — лише метадані очищеної версії.
- Семантика колонок вводиться Provider при підготовці набору до публікації; для демо-наборів значення беруться з розділу 2 цього документа.
- Зміни полів картки (додавання/перейменування) вносяться спочатку сюди, потім у UC-12, схему відповіді API і UI.

## Відкриті питання

1. Де зберігати «Опис» і «Семантику колонок» (нові поля `Dataset` або окрема таблиця) і хто із команди додає їх у API і UI.
2. Які саме поля додати в `/api/catalog` для Consumer: колонки, правову підставу, `retention_until`.
3. Домен email маскується повністю (`i***.com`). Для аналітики рекламного агентства, можливо, потрібен лише домен; питання для PO.
4. Усунути розбіжність №3: відкидати reject-рядки при очищенні. Після цього замінити «ціль» 484 / 950 на фактичні значення.
5. Значення HMAC залежить від `HMAC_KEY`; у прикладах використано тестовий ключ.
6. Баг: `pd.read_json` читає `phone` з `customers.json` як `int64` і губить `+`, через що телефон маскується як `******0963`, а не `+380*****63`. Посилання на баг: _буде додано після заведення задачі (виконавець — Назар)_. Після виправлення оновити приклад і формат у розділі 2.2.
