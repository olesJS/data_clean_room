# Демо Data Clean Room (Sprint 3)

Покроковий сценарій демонстрації повного циклу: **завантаження → профілювання → PII review → правова підстава → анонімізація → публікація → запит на доступ → схвалення → завантаження clean-версії → аудит**.

Тривалість: 12–15 хвилин. Потрібен Docker Desktop і свіжа база.

## 1. Підготовка

Скопіюйте `.env.example` у `.env` і за потреби задайте власні секрети **до** запуску стека:

```bash
cp .env.example .env
```

Потім підніміть чисту базу та застосунок:

```bash
docker compose down -v
docker compose up --build -d
```

Зачекайте, поки backend відповість:

```bash
curl http://localhost:8000/health
```

> `HMAC_KEY` обов’язковий у production. У development/test без нього використовується детермінований демонстраційний ключ; для реальних даних задайте `HMAC_KEY` у `.env`.

Наповніть демо-даними (створює два опубліковані набори та один схвалений запит):

```bash
python scripts/demo_seed.py
```

Скрипт працює через публічний API і використовує лише демонстраційні акаунти.

### Акаунти

| Роль | Email | Пароль |
|---|---|---|
| Data Provider | `provider@example.com` | `password123` |
| Data Consumer | `consumer@example.com` | `password123` |
| Data Steward | `steward@example.com` | `password123` |

Усі три користувачі створюються автоматично у development/test (`SEED_USERS=true`).

## 2. Сценарій демонстрації

### Крок 1. Data Provider: завантаження та профіль

1. Увійдіть як `provider@example.com`.
2. **Імпортувати дані** → виберіть `data/payroll.csv` (або `data/customers.json`).
3. Відкрийте набір → **Профіль**: кількість рядків, пропуски, дублікати, викиди, Quality Score.
4. Покажіть, що клас набору — `Personal`, бо знайдено PII.

Що підкреслити: сирий файл зберігається окремо, але назовні його ніколи не віддають.

### Крок 2. PII review

1. На сторінці набору відкрийте **PII сканування**.
2. Покажіть колонки з типом PII, confidence і маскованими прикладами.
3. Підтвердьте одну-дві знахідки або виправте тип.

Що підкреслити: `user_confirmed = false` виключає колонку з активного PII-набору; виправлення типу впливає на публікаційні ворота.

### Крок 3. Правова підстава

1. **Публікація** → блок **Правові підстави** (або `/datasets/{id}/legal`).
2. **Додати підставу**: тип `consent`, мета `analytics`, документ `DEMO-CONSENT-1`, дата — сьогодні, діє до — +1 рік.
3. Покажіть, що підстава активна.

Що підкреслити: мета має збігатися з метою запиту; HMAC-псевдонімізація без чинної підстави блокує публікацію.

### Крок 4. Анонімізація: preview → apply

1. На сторінці **Публікація** покажіть таблицю PII-колонок і методи.
2. Натисніть **Попередній перегляд**.
   - Файл і версія **не створюються**.
   - Показується очікуваний клас і методи по колонках.
3. Натисніть **Застосувати анонімізацію**.
   - Створюється незмінна clean-версія `vN`.
   - У таблиці версій з’являється `clean`, SHA-256 і кількість рядків.
4. Відкрийте **Версії**: оригінал і clean-версія розділені.

Що підкреслити: за замовчуванням ПІБ/адреса/email/телефон маскуються, дата народження узагальнюється, ІПН/паспорт/IBAN/картка псевдонімізуються через HMAC. Клас після HMAC лишається `Personal`.

### Крок 5. Publication gate

1. Вкажіть **Зберігати до** (+180 днів).
2. **Перевірити готовність** — перевірка read-only.
3. Покажіть, що всі чотири умови виконані:
   - є clean-версія;
   - кожна PII-колонка оброблена;
   - для HMAC є чинна правова підстава;
   - retention задано.
4. **Опублікувати**.
5. Покажіть новий клас, статус `Published` і запис `PUBLISH` в аудиті.

Негативний показ (за бажанням): відкличте правову підставу й натисніть **Перевірити готовність** — з’явиться `hmac_without_legal_basis`, публікація заблокується.

### Крок 6. Data Consumer: каталог і запит

1. Вийдіть і увійдіть як `consumer@example.com`.
2. **Каталог**: лише опубліковані набори; сирих файлів немає.
3. **Запросити доступ** → мета `analytics` → надіслати.
4. **Мої запити**: статус `Requested` (очікує рішення).

Що підкреслити: мета перевіряється на етапі запиту; невідповідна мета дає `403 legal_basis_invalid: purpose_mismatch`; дубль активного запиту — `409`.

### Крок 7. Data Provider: рішення

1. Увійдіть як `provider@example.com` → **Запити на доступ**.
2. Відкрийте запит → **Схвалити**, доступ до +30 днів, коментар.
3. Покажіть, що запит зник з черги «очікують» і має статус `Approved`.

Негативний показ: Data Steward бачить усі запити, але кнопки рішення для нього недоступні — рішення ухвалює лише власник набору.

### Крок 8. Data Consumer: завантаження

1. Увійдіть як `consumer@example.com` → **Мої запити**.
2. **Завантажити** — віддається лише clean-версія.
3. Відкрийте файл: у колонках ПІБ/ІПН стоять маски/псевдоніми, сирих значень немає.
4. Статус змінюється на `Downloaded`, в аудиті з’являється `DOWNLOAD`.

Що підкреслити: повторне завантаження в межах `access_until` дозволене; після `access_until` — `403 access_expired`, статус `Expired`.

### Крок 9. Data Steward: аудит

1. Увійдіть як `steward@example.com` → **Журнал аудиту**.
2. Покажіть послідовність: `LOGIN`, `UPLOAD_DATASET`, `CREATE_LEGAL_BASIS`, `ANONYMIZE`, `PUBLISH_CHECK`, `PUBLISH`, `REQUEST`, `REQUEST_APPROVED`, `DOWNLOAD`.
3. Відфільтруйте результат `DENY` — причина відмови є в `object`, але без PII, `document_ref` і тексту коментарів.
4. Покажіть, що Steward не має доступу до вмісту наборів.

## 3. Негативні сценарії (2–3 хвилини)

| Сценарій | Очікування |
|---|---|
| Consumer відкриває `/datasets` | Лише опубліковані набори, сирих немає |
| Consumer створює запит із метою `research` до підстави `analytics` | `403`, `purpose_mismatch`, аудит `DENY` |
| Provider відкликає підставу, потім схвалює вже створений запит | `403`, `revoked`, аудит `DENY` |
| Після відкликання підстави Consumer натискає «Завантажити» | `403`, `legal_basis_invalid: revoked` |
| Data Steward намагається схвалити запит | `403`, рішення лише власник |
| Публікація без анонімізації | `422`, `no_clean_version` + `pii_not_processed` |
| Публікація HMAC без підстави | `422`, `hmac_without_legal_basis` |
| Публікація без retention | `422`, `retention_required` |
| Чужий Provider відкриває запит | `404` (не розкриває існування) |

## 4. API-версія сценарію

```bash
# Логін
curl -s -X POST http://localhost:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"provider@example.com","password":"password123"}'

# Каталог (Consumer)
curl -s http://localhost:8000/api/catalog \
  -H "Authorization: Bearer $CONSUMER_TOKEN"

# Запит на доступ
curl -s -X POST http://localhost:8000/api/exchange-requests \
  -H "Authorization: Bearer $CONSUMER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"dataset_id":1,"purpose":"analytics"}'

# Схвалення (Provider)
curl -s -X POST http://localhost:8000/api/exchange-requests/1/approve \
  -H "Authorization: Bearer $PROVIDER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"access_until":"2026-12-31","review_comment":"Demo approval"}'

# Завантаження clean-версії
curl -L http://localhost:8000/api/exchange-requests/1/download \
  -H "Authorization: Bearer $CONSUMER_TOKEN" -o clean.csv
```

Повний контракт — у Swagger UI: <http://localhost:8000/docs>.

## 5. Якщо щось не працює

| Симптом | Причина / рішення |
|---|---|
| `401` після входу | Протух токен; увійдіть повторно |
| Порожній каталог | Набори не опубліковані; перевірте `PUBLISH` в аудиті |
| `no_clean_version` | Спочатку застосуйте анонімізацію (не лише preview) |
| `hmac_without_legal_basis` | Додайте активну підставу з метою або замініть HMAC на mask/generalize |
| `purpose_mismatch` | Мета запиту не збігається з метою підстави |
| `Dataset is already published` | Набір уже опубліковано; для нової clean-версії створіть новий набір або використайте нову версію |
| Демо-скрипт падає з `Login failed` | Backend ще стартує або БД не свіжа; перевірте `/health` і `docker compose logs backend` |
| Після зміни схеми БД помилки | Alembic у проєкті немає: `docker compose down -v`, потім повторний старт |

## 6. Безпека демонстрації

- Не використовуйте реальні персональні дані: лише `data/payroll.csv` і `data/customers.json`.
- Не показуйте `.env`, `SECRET_KEY`, `HMAC_KEY` і логи з токенами.
- Clean-файл містить маски/псевдоніми, але поводьтеся з ним як із конфіденційним.
- Аудит не містить PII, `document_ref` або причин відкликання — це можна показати як перевагу.
