# Тест-кейси: UC-01 «Автентифікуватися в системі» та UC-02 «Завантажити сирий набір даних»

Документ містить основні тест-кейси до специфікацій прецедентів UC-01 і UC-02. Він лежить у репозиторії в `docs/testing/`. Повніший набір сценаріїв, які залишено на потім, перелічено в розділі 4.

> **Статус.** Кейси складено за специфікаціями та за кодом бекенду з PR #5 (JWT, RBAC, аудит, завантаження). Позначка **⚠** означає, що за прочитаним кодом очікується розбіжність зі специфікацією (розділ 5).

## 0. Відповідність плану проєкту

План (Спринт 1, роль A, 2 SP, епік E9, мітка `qa`) вимагає: «TC-01 і TC-N1 для UC-01, TC-02 і TC-N6 для UC-02 у форматі "кроки → очікуваний результат"».

| ID плану | Сценарій за планом | Кейси в документі |
| --- | --- | --- |
| TC-01 | Вхід із коректними обліковими даними: токен видано, меню відповідає ролі | TC-01.1 – TC-01.3 |
| TC-N1 | Негативний вхід і доступ без токена: відмова 401 | TC-N1.1 – TC-N1.4 |
| TC-02 | Завантаження коректного CSV кейсу 1: створено сиру версію, показано профіль | TC-02.1 – TC-02.4 |
| TC-N6 | Порожній файл, непідтримуваний формат, некоректний JSON: зрозуміла помилка, сервіс не падає | TC-N6.1 – TC-N6.6 |

Разом **17 кейсів**: 7 для UC-01 і 10 для UC-02.

## 1. Середовище і дані

**Запуск:** `docker compose up --build -d`. Інтерфейс: http://localhost, API: http://localhost:8000, Swagger: http://localhost:8000/docs.

**Тестові акаунти** (створюються при старті, лише для розробки; пароль для всіх `password123`):

| Роль | Email |
| --- | --- |
| Data Provider | provider@example.com |
| Data Consumer | consumer@example.com |
| Data Steward | steward@example.com |

**Файли з `data/`** (опис дефектів у `data/defects.md`):

| Файл | Призначення |
| --- | --- |
| `payroll.csv` | Кейс 1: 500 рядків, 8 колонок |
| `customers.json` | Кейс 2: 1000 записів, 8 полів |
| `invalid/empty.csv`, `empty.json` | Файли по 0 байт |
| `invalid/not_supported.txt` | Звичайний текст |
| `invalid/bad_syntax.json` | Пропущена кома, помилка в 4-му рядку (`line 4 column 3`) |

**Запис в аудиті** означає рядок у `audit_logs` (або у відповіді `GET /audit` від Data Steward) з полями: хто (actor), коли (timestamp), дія (action), об'єкт (object), результат (result). Пароль і вміст файлів у журнал потрапляти не повинні.

## 2. UC-01. Автентифікація

### TC-01.1 Успішний вхід Data Provider · P1 · авто + вручну
- **Передумови:** сервіс запущено, користувач не автентифікований.
- **Дані:** `provider@example.com` / `password123`.
- **Кроки:**
  1. Відкрити сторінку входу, ввести email і пароль, натиснути «Увійти» (API: `POST /api/auth/login` з тілом `{"email", "password"}`).
- **Очікуваний результат:**
  - 200; у тілі `access_token` (JWT), `token_type = "bearer"`, `role = "DataProvider"`.
  - Інтерфейс показує меню Provider (завантаження, мої набори).
  - В аудиті запис: actor `provider@example.com`, action `LOGIN`, result успіх, timestamp поточний.
  - У JWT є claims `role` і `exp`, але немає пароля чи його хеша.

### TC-01.2 Успішний вхід Data Consumer і Data Steward · P1 · авто + вручну
- **Дані:** `consumer@example.com` і `steward@example.com` / `password123`.
- **Кроки:** як у TC-01.1, окремо для кожного акаунта; потім `GET /api/auth/me` з отриманим токеном.
- **Очікуваний результат:**
  - Consumer: `role = "DataConsumer"`, меню без завантаження наборів і журналу.
  - Steward: `role = "DataSteward"`, меню з журналом аудиту, без перегляду вмісту наборів.
  - `/me` повертає `{id, email, role}` акаунта без пароля й хеша.
  - Для обох входів є записи `LOGIN` з успіхом.

### TC-01.3 AC1. Термін дії токена минув · P2 · авто + вручну
- **Кроки:**
  1. Сформувати токен з `exp` у минулому (у тесті `create_access_token(..., expires_delta=timedelta(seconds=-1))`).
  2. Викликати `GET /api/auth/me`.
  3. У браузері підставити протермінований токен і оновити сторінку.
- **Очікуваний результат:** 401 `Not authenticated`; інтерфейс перенаправляє на сторінку входу; повторний вхід відновлює доступ.
- **Примітка:** перенаправлення залежить від реалізації фронтенду.

### TC-N1.1 EX1. Неправильні облікові дані · P1 · авто + вручну · ⚠
- **Дані:** (a) `provider@example.com` / `wrong_pwd`; (b) `nobody@example.com` / `password123`.
- **Кроки:** `POST /api/auth/login` для (a) і (b); порівняти відповіді.
- **Очікуваний результат:**
  - 401, токен не видається.
  - Повідомлення **не уточнює**, що саме хибне, і **однакове** для (a) і (b) (неможливо дізнатися, чи існує акаунт). За специфікацією: «Невірний логін або пароль».
  - В аудиті запис `LOGIN` з результатом відмова і введеним email як actor; пароля в журналі немає.
- **Розбіжність:** бекенд повертає англійською `Invalid credentials`.

### TC-N1.2 EX3. Запит до API без токена · P1 · авто · ⚠
- **Кроки:** без заголовка `Authorization` викликати `GET /api/auth/me`, `POST /datasets`, `GET /audit`.
- **Очікуваний результат:** на всі три 401 `{"detail": "Not authenticated"}`, дані не віддаються.
- **Розбіжність:** `GET /datasets` у PR #5 теж відкритий без токена, а відмови 401 не записуються в аудит, хоча специфікація цього вимагає.

### TC-N1.3 Підроблений токен · P1 · авто
- **Кроки:** викликати `GET /audit` з такими токенами: (a) випадковий рядок; (b) токен provider, у payload якого змінено `role` на `DataSteward` без перепідпису; (c) токен, підписаний іншим ключем.
- **Очікуваний результат:** у всіх випадках 401 без 500; підвищити роль підробкою токена неможливо.

### TC-N1.4 Контроль доступу за ролями (RBAC) · P1 · авто · ⚠
- **Кроки:** з токеном кожної ролі викликати `GET /audit`.
- **Очікуваний результат:**

| Роль | `GET /audit` |
| --- | --- |
| Data Provider | 403 |
| Data Consumer | 403 |
| Data Steward | 200 |

  Відмова 403 містить зрозуміле повідомлення і записується в аудит.
- **Розбіжність:** у PR #5 відмови 403 в аудит не пишуться.

## 3. UC-02. Завантаження набору

**Спільні передумови:** користувач автентифікований як Data Provider (TC-01.1). Запит: `POST /datasets` (`multipart/form-data`, поле `file`, необов'язкове `name`).

### TC-02.1 Завантаження зарплатної відомості (CSV, кейс 1) · P1 · авто + вручну
- **Дані:** `data/payroll.csv`, назва «Зарплатні відомості 2026-09».
- **Кроки:**
  1. На екрані імпорту (або через API) обрати файл, вказати назву, натиснути «Імпортувати».
- **Очікуваний результат:**
  - 201; `original_filename = "payroll.csv"`, `file_type = "csv"`, `row_count = 500`, `file_size` дорівнює розміру файлу.
  - У `columns` усі 8 колонок: `employee_id, full_name, ipn, iban, position, department, amount_uah, payment_date`.
  - Файл прийнято **попри закладені дефекти** (порожні ІПН, дублікати, суми ≤ 0, майбутні дати): якість оцінюється в UC-03/04. Дублікати не видаляються (`row_count = 500`, а не 490).
  - Інтерфейс показує підтвердження і відкриває профіль набору (UC-03).

### TC-02.2 Завантаження бази клієнтів (JSON, кейс 2) · P1 · авто + вручну
- **Дані:** `data/customers.json`, назва «Клієнти ритейлу».
- **Кроки:** як у TC-02.1.
- **Очікуваний результат:** 201, `file_type = "json"`, `row_count = 1000`, 8 полів (`customer_id, full_name, email, phone, birth_date, age, city, registration_date`). Записи з `null` і `""` у `city`, некоректним віком, email і датами лишаються в наборі.

### TC-02.3 Сира версія незмінна, подія в аудиті · P1 · авто · ⚠
- **Кроки:**
  1. Порахувати SHA-256 файлу `payroll.csv`.
  2. Завантажити файл (TC-02.1) і порахувати SHA-256 збереженого файлу (`storage/datasets/<uuid>_payroll.csv`).
  3. Завантажити той самий файл вдруге.
  4. Увійти як Data Steward, викликати `GET /audit`.
- **Очікуваний результат:**
  - Хеші збігаються байт у байт.
  - Друге завантаження створює окремий запис і окремий файл, перший не перезаписується.
  - В аудиті запис завантаження: actor `provider@example.com`, дія завантаження, назва набору, результат успіх, timestamp. Steward бачить метадані, але не вміст файлу.
- **Розбіжність:** дія в PR #5 називається `UPLOAD_DATASET`, у специфікації `UPLOAD`; результати `SUCCESS`/`FAILURE` проти «успіх/відмова». Потрібен спільний довідник подій.

### TC-02.4 Визначення типів колонок · P1 · авто · ⚠
- **Передумови:** набори з TC-02.1 і TC-02.2 завантажено.
- **Кроки:** переглянути `columns` у відповіді або в переліку наборів.
- **Очікуваний результат:**

| Колонка | Тип |
| --- | --- |
| `employee_id`, `full_name`, `iban`, `email`, `phone` | текст |
| `ipn` | **текст** (ідентифікатор), не число |
| `amount_uah` | число з десятковою частиною |
| `customer_id`, `age` | ціле число |
| `payment_date`, `registration_date`, `birth_date` | дата або текст ISO |

- **Розбіжність:** `pandas.read_csv` без `dtype=str` визначає `ipn` як `float64` (через порожні значення), і ІПН втрачає форму. Якщо `ipn` повертається як число, це дефект.

**Спільна перевірка для всіх TC-N6.** Після відмови: (1) у БД не створено набір, (2) у сховищі немає файлу, (3) в аудиті є запис про спробу з результатом відмова, (4) `GET /health` повертає 200, (5) відповідь не містить стека викликів.

- **Дані:** `data/invalid/empty.csv`, `data/invalid/empty.json`.
- **Кроки:** завантажити кожен файл.
- **Очікуваний результат:** 400 з повідомленням «Файл порожній»; спільна перевірка.

### TC-N6.2 EX2. Непідтримуваний формат · P1 · авто + вручну
- **Дані:** `data/invalid/not_supported.txt`, а також `report.xlsx` і `payroll.csv.exe` (будь-які файли з такими іменами).
- **Очікуваний результат:** 400 з текстом, що дозволено лише CSV і JSON; спільна перевірка; сервіс не падає.

### TC-N6.3 EX3. Некоректний JSON · P1 · авто + вручну
- **Дані:** `data/invalid/bad_syntax.json`.
- **Очікуваний результат:** 400; повідомлення **вказує місце помилки** (рядок 4, стовпець 3); спільна перевірка.

### TC-N6.4 EX4. Перевищено розмір файлу · P1 · вручну + авто
- **Дані:** `too_large.csv` (≈51 МБ).
- **Кроки:** завантажити файл. В автотесті замість великого файлу змінити `MAX_FILE_SIZE` на малий і перевірити межу: рівно ліміт приймається, ліміт + 1 байт відхиляється.
- **Очікуваний результат:** 400 із поясненням ліміту (50 МБ); запит завершується без таймауту й падіння контейнера; спільна перевірка.

### TC-N6.5 EX5. Завантаження без права · P1 · авто · ⚠
- **Кроки:** `POST /datasets` з валідним `payroll.csv`: (a) токеном Data Consumer; (b) токеном Data Steward; (c) без токена.
- **Очікуваний результат:** (a) і (b) 403, (c) 401; набір не створено, файл не збережено; відмова записана в аудит.
- **Розбіжності:**
  - У PR #5 дозволено ролі `DataProvider` і `DataSteward`, тому (b) **прийметься**. За специфікацією (UC-02, актор лише Data Provider) це дефект, або це рішення треба внести в специфікацію.
  - Відмови (a) і (c) у PR #5 в аудит не пишуться.

### TC-N6.6 Відсутність побічних ефектів після помилок · P2 · авто
- **Кроки:** запам'ятати кількість наборів у БД і файлів у сховищі; виконати TC-N6.1 – TC-N6.5; порівняти.
- **Очікуваний результат:** кількість наборів і файлів не змінилась; в аудиті рівно один запис відмови на кожну спробу; немає «напівстворених» станів (файл є, а запису немає, або навпаки).
