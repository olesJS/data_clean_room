Документ містить тест-кейси до прецедентів обміну даними (SCRUM-67). Формат той самий, що в `test-cases-uc01-uc02.md` і `test-cases-uc03-uc05.md`. Додано наскрізний сценарій обов'язкового демо (методичні вказівки, розділ 5.1).

> **Статус.** Кейси складено за специфікаціями UC-06 – UC-10 і UC-14 (`UC_Specifications_DCR.docx`, PR #38), governance 3.3 – 3.5, Activity- і Sequence-діаграмами та кодом `main` на коміті `05e0707` (22.11.2026: PR #41 – #46). Очікувані результати описують поведінку за специфікацією. Якщо код поводиться інакше, кейс фіксує дефект. Позначка **⚠** означає відому розбіжність коду зі специфікацією (розділ 9).

**Запуск:** як у `test-cases-uc01-uc02.md`, розділ 1. Перед запуском створити `.env` з `.env.example` і заповнити `HMAC_KEY` (`python -c "import secrets; print(secrets.token_hex(32))"`). Після оновлення з версії без Alembic один раз виконати `docker compose down -v`.

**Акаунти** (пароль `password123`):

| Роль | Акаунт |
| --- | --- |
| Data Provider (власник наборів) | `provider@example.com` |
| Data Provider (інший) | створюється вручну або фікстурою (`provider2@example.com`) |
| Data Consumer | `consumer@example.com` |
| Data Consumer (інший) | створюється вручну або фікстурою (`consumer2@example.com`) |
| Data Steward | `steward@example.com` |

**Набори і PII** (з `test-cases-uc03-uc05.md`, TC-04.1, TC-04.2):

| Набір | Рядків | PII-колонки | Клас після сканування |
| --- | --- | --- | --- |
| `data/payroll.csv` | 500 | `full_name`, `ipn`, `iban` | Personal |
| `data/customers.json` | 1000 | `full_name`, `email`, `phone` | Personal |
| `data/pii/traps.csv` | — | немає | Internal |

**Методи анонімізації** (`backend/app/services/anonymizer.py`):

| Метод | API | Приклад | Клас після публікації |
| --- | --- | --- | --- |
| Маскування | `mask` | `ivan.petrenko@domain.com` → `i***@d***.com`; `+380501234567` → `+380*****67`; ІПН/IBAN → `******` + останні 4 символи; ім'я → перша літера + `***` + остання | Confidential |
| Узагальнення | `generalize` | дата → рік; вік → десятиліття (`34` → `30-39`); адреса → частина до першої коми. Лише для колонок з датою, віком, адресою чи містом | Confidential |
| HMAC-SHA256 | `hmac` | 64 hex-символи, детерміновано для одного ключа | Personal (псевдонімізація) |

**Мета обробки:** `analytics`, `research`, `reporting`, `publication` (enum `LegalBasisPurpose`). У запиті Consumer мета — текст від 10 символів. UI передає її у форматі `analytics: <опис>`, а бекенд виділяє категорію за ключовим словом.

**Ендпоінти:**

| Дія | Ендпоінт |
| --- | --- |
| Прев'ю / застосування анонімізації | `POST /api/datasets/{id}/anonymize/preview`, `POST /api/datasets/{id}/anonymize` |
| Правова підстава | `POST`/`GET /api/datasets/{id}/legal-basis`, `POST /api/legal-basis/{id}/revoke` |
| Ворота / публікація | `GET /api/datasets/{id}/publish/check`, `POST /api/datasets/{id}/publish` |
| Каталог | `GET /api/catalog` |
| Запити | `POST`/`GET /api/requests`, `POST /api/requests/{id}/approve`, `/reject`, `GET /api/requests/{id}/download` |

**Події аудиту** (governance 3.4): `UPLOAD_DATASET`, `PII_SCAN`, `ANONYMIZE`, `PUBLISH`, `DENY`, `REQUEST`, `REQUEST_APPROVED`, `REQUEST_REJECTED`, `DOWNLOAD`, `CONSENT_REVOKED`, `REVOKE_LEGAL_BASIS`, `ACCESS_DENIED`. Значення PII, HMAC-ключ і номер документа правової підстави в журнал потрапляти не повинні.

## 2. UC-06. Анонімізація набору

### TC-05.1 Прев'ю маскування (payroll.csv) · P1 · авто + вручну
- **Передумови:** `payroll.csv` завантажено і проскановано від імені `provider@example.com`.
- **Кроки:** на сторінці «Анонімізація» обрати `mask` для `full_name`, `ipn`, `iban` і натиснути «Попередній перегляд».
- **Очікуваний результат:**
  - Для кожної з трьох колонок показано 10 пар «до → після».
  - `ipn` і `iban` мають вигляд `******` + останні 4 символи; `full_name` — перша літера, `***`, остання літера.
  - Інші колонки у відповіді не повертаються.
  - Очищена версія не створюється: у `dataset_versions` немає запису `clean`, подія `ANONYMIZE` не пишеться.

### TC-05.2 Застосування анонімізації створює clean-версію · P1 · авто + вручну
- **Передумови:** TC-05.1.
- **Кроки:** натиснути «Застосувати» з тими самими методами.
- **Очікуваний результат:**
  - Відповідь містить `clean_sha256`, `row_count = 500`, `applied_columns = [full_name, ipn, iban]`.
  - У `dataset_versions` є запис `kind = clean` з SHA-256 файлу.
  - Сирий файл не змінився: SHA-256 версії `raw` такий самий, як до анонімізації.
  - У `anonymization_methods` три записи, по одному на колонку.
  - В аудиті `ANONYMIZE` з actor `provider@example.com`, без значень PII.

### TC-05.3 Маскування контактів (customers.json) · P1 · авто + вручну
- **Кроки:** для `customers.json` застосувати `mask` до `full_name`, `email`, `phone`.
- **Очікуваний результат:**
  - `email` у форматі `x***@y***.domain`, `phone` у форматі `+380*****NN`.
  - Clean-версія зберігається у форматі JSON (`row_count = 1000`).

### TC-05.4 Узагальнення дати і віку · P2 · авто
- **Кроки:** для `customers.json` виконати прев'ю з `generalize` для `birth_date` і `age`.
- **Очікуваний результат:** `1977-09-15` → `1977`; `49` → `40-49`; порожні значення лишаються порожніми.

### TC-05.5 HMAC детермінований і залежить від ключа · P1 · авто
- **Кроки:**
  1. Застосувати `hmac` до `ipn` у `payroll.csv`.
  2. Повторити анонімізацію з тим самим ключем.
  3. Повторити з іншим `HMAC_KEY` (лише в тестовому середовищі).
- **Очікуваний результат:**
  - Значення `ipn` — 64 hex-символи; однакові ІПН дають однаковий хеш.
  - Крок 2: хеші ті самі. Крок 3: хеші інші.
  - Порожні ІПН (15 рядків) лишаються порожніми.
  - HMAC-ключ не з'являється ні у відповіді API, ні в аудиті, ні в логах.

### TC-N5.1 Доступ за ролями · P1 · авто
- **Кроки:** викликати preview і apply для набору `provider@example.com`:
  - (a) від `provider2@example.com`;
  - (b) від Consumer;
  - (c) від Steward;
  - (d) без токена.
- **Очікуваний результат** (рішення PO 8): (a) 404; (b) 403; (c) 403; (d) 401. Відмови (a)–(c) записано в аудит як `ACCESS_DENIED`. Clean-версія не створюється.

### TC-N5.2 Узагальнення непідтримуваної колонки · P1 · авто
- **Кроки:** preview і apply з `generalize` для `full_name` або `ipn`.
- **Очікуваний результат:** 422 «Generalization is not supported for column …». Clean-версія не створюється, методи не записуються.

### TC-N5.3 Невідомий метод або неіснуюча колонка · P2 · авто
- **Кроки:** (a) метод `redact`; (b) колонка `salary`, якої немає в наборі.
- **Очікуваний результат:** обидва 422 з поясненням. Clean-версія не створюється.

### TC-N5.4 Сервер без HMAC-ключа · P1 · вручну
- **Кроки:** видалити `HMAC_KEY` з `.env` і виконати `docker compose up`.
- **Очікуваний результат:** compose зупиняється з повідомленням «Set HMAC_KEY in .env». Сервіс не стартує з ключем за замовчуванням.

## 3. UC-07. Публікація (ворота)

### TC-06.1 Повністю замаскований набір → Confidential · P1 · авто + вручну
- **Передумови:** TC-05.2 (усі PII замасковано).
- **Кроки:**
  1. Відкрити «Публікація», вказати термін зберігання (дата в майбутньому).
  2. Переглянути чек-лист воріт.
  3. Натиснути «Опублікувати».
- **Очікуваний результат:**
  - Крок 2: усі 5 пунктів ✔ (очищена версія, PII оброблено, HMAC без підстави — не застосовно, термін, правила якості). `GET /publish/check` нічого не змінює в БД.
  - Крок 3: статус `published`, клас **Confidential**, заповнено `published_at`, `published_by`, `retention_until`.
  - В аудиті `PUBLISH` з класом і терміном.
  - Набір з'явився в каталозі Consumer.

### TC-06.2 HMAC з чинною правовою підставою → Personal · P1 · авто + вручну
- **Передумови:** `payroll.csv`: `full_name`, `iban` — `mask`, `ipn` — `hmac`.
- **Кроки:**
  1. Додати правову підставу: тип «згода», мета `analytics`, документ, дійсна до — дата в майбутньому.
  2. Опублікувати з терміном зберігання.
- **Очікуваний результат:** публікація успішна, клас **Personal**. Мета підстави на публікації не перевіряється (рішення PO, governance 3.5).

### TC-06.3 Набір без PII → Internal · P2 · авто
- **Дані:** `data/pii/traps.csv` (PII немає).
- **Кроки:** застосувати анонімізацію без колонок (`columns = {}`), опублікувати.
- **Очікуваний результат:** клас **Internal**, публікація успішна.

### TC-06.4 Підказка про правову підставу для обміну · P2 · вручну
- **Кроки:** відкрити «Публікація» для набору без правової підстави.
- **Очікуваний результат:** видно підказку «Без правової підстави запити на цей набір не можна буде схвалити» (UC-07, примітка).

### TC-N6.1 Немає очищеної версії · P1 · авто
- **Кроки:** опублікувати одразу після завантаження, без анонімізації.
- **Очікуваний результат:** 422, причина `no_clean_version`; статус лишається `uploaded`; в аудиті `DENY` з причиною.

### TC-N6.2 Не всі PII-колонки оброблено · P1 · авто + вручну
- **Кроки:** застосувати `mask` лише до `full_name` і `iban` (без `ipn`), опублікувати.
- **Очікуваний результат:** 422, причина `pii_not_processed` з колонкою `ipn`; у чек-листі UI пункт «PII оброблено» ✘ з назвою колонки; `DENY` в аудиті.

### TC-N6.3 HMAC без чинної підстави · P1 · авто
- **Кроки:** (a) `ipn` — `hmac`, правової підстави немає; (b) підстава є, але відкликана; (c) підстава прострочена.
- **Очікуваний результат:** 422, причина `hmac_without_legal_basis`; у (b) і (c) з уточненням `revoked` / `expired`; `DENY` в аудиті.

### TC-N6.4 Немає терміну зберігання або він у минулому · P1 · авто
- **Кроки:** опублікувати з `retention_until` вчора.
- **Очікуваний результат:** 422, причина `retention_required`.

### TC-N6.5 Повторна публікація · P2 · авто
- **Кроки:** опублікувати вже опублікований набір.
- **Очікуваний результат:** 409 «Dataset is already published»; клас і дати не змінюються.

### TC-N6.6 Доступ за ролями · P1 · авто
- **Кроки:** `publish/check` і `publish` від іншого Provider, Consumer, Steward, без токена.
- **Очікуваний результат:** 404, 403, 403, 401. Відмови в аудиті.

## 5. UC-09. Розгляд запиту

### TC-08.1 Власник схвалює запит · P1 · авто + вручну
- **Передумови:** TC-07.2, для набору є чинна підстава з метою `analytics`.
- **Кроки:** від `provider@example.com` відкрити «Запити на доступ», «Схвалити» з коментарем.
- **Очікуваний результат:**
  - Статус `approved`, заповнено `reviewed_by`, `reviewed_at`, коментар.
  - В аудиті `REQUEST_APPROVED`.
  - Consumer бачить статус «Схвалено» і кнопку «Завантажити».

### TC-08.2 Власник відхиляє запит · P1 · авто
- **Кроки:** «Відхилити» з коментарем.
- **Очікуваний результат:** статус `rejected`, коментар видно Consumer; в аудиті `REQUEST_REJECTED`; кнопки завантаження немає.

### TC-N8.1 Схвалення не власником · P1 · авто + вручну
- **Кроки:** approve / reject від (a) `provider2@example.com`; (b) Steward; (c) Consumer.
- **Очікуваний результат:**
  - (a) 404 (рішення PO 8); (b), (c) 403, `ACCESS_DENIED` в аудиті.
  - В UI Steward бачить сторінку «Запити на доступ» лише для перегляду, без кнопок «Схвалити/Відхилити».

### TC-N8.2 Правова підстава недійсна при схваленні · P1 · авто
- **Кроки:** схвалити запит, коли (a) підстави немає; (b) підставу відкликано; (c) вона прострочена; (d) мета запиту `research`, а підстава лише на `analytics`.
- **Очікуваний результат:**
  - 409 з причиною: (a) `no_legal_basis`, (b) `revoked`, (c) `expired`, (d) `purpose_mismatch`.
  - Запит лишається `pending`, а не `rejected` (рішення PO, `sequence-exchange.puml`).
  - В аудиті `DENY`.
- **Примітка:** підстава потрібна при кожному схваленні, навіть для класу Confidential чи Internal (рішення PO від 15.11, UC-09).

### TC-N8.3 Повторне рішення · P2 · авто
- **Кроки:** схвалити вже схвалений або відхилений запит.
- **Очікуваний результат:** 409; статус не змінюється.

### TC-N8.4 Неіснуючий запит · P3 · авто
- **Кроки:** approve для `request_id = 99999`.
- **Очікуваний результат:** 404.

- **Передумови:** `customers.json` замасковано, опубліковано, запит схвалено.

### TC-N9.1 Завантаження без схвалення · P1 · авто
- **Кроки:** download для запиту в статусі (a) `pending`; (b) `rejected`.
- **Очікуваний результат:** 403; в аудиті `DENY`; файл не віддається.

### TC-N9.2 Чужий запит · P1 · авто
- **Кроки:** download від `consumer2@example.com`, від Provider і від Steward.
- **Очікуваний результат:** 404 (рішення PO 8); з відповіді не видно, що запит існує.

### TC-N9.3 Згоду відкликано після схвалення · P1 · авто + вручну
- **Кроки:**
  1. Запит схвалено (TC-08.1).
  2. Власник відкликає згоду (TC-10.1).
  3. Consumer натискає «Завантажити».
- **Очікуваний результат:** 403 з причиною `revoked`; в аудиті `DENY`; UI показує «Згоду відкликано — завантаження неможливе».

### TC-N9.4 Повторне завантаження · P2 · авто · ⚠
- **Кроки:** після TC-09.1 завантажити файл ще раз.
- **Очікуваний результат (UC-10, AC2):** повторне завантаження дозволено, поки підстава чинна і термін зберігання не минув; кожне завантаження пишеться в аудит.

## 7. UC-14. Відкликання згоди

### TC-10.1 Власник відкликає згоду · P1 · авто + вручну
- **Кроки:** від `provider@example.com` на сторінці публікації натиснути «Відкликати згоду», вказати причину, підтвердити в модальному вікні.
- **Очікуваний результат:**
  - Заповнено `revoked_at`, `revoked_by`, `revoked_reason`; статус підстави «Відкликано».
  - В аудиті `CONSENT_REVOKED`, у записі немає номера документа і тексту причини.
  - Нові схвалення і завантаження за цією підставою блокуються (TC-N8.2 b, TC-N9.3).

### TC-10.2 Steward відкликає згоду · P1 · авто + вручну
- **Кроки:** від Steward на сторінці «Запити на доступ» відкликати підставу набору.
- **Очікуваний результат:** як у TC-10.1, actor — `steward@example.com`.

### TC-10.3 Відкликання договору чи закону через API · P3 · авто
- **Кроки:** `POST /api/legal-basis/{id}/revoke` для підстави типу `contract`.
- **Очікуваний результат:** 200, підставу відкликано (UC-14: будь-який тип через API; кнопка в UI лише для згоди).

### TC-N10.1 Consumer не може відкликати · P1 · авто
- **Очікуваний результат:** 403; `REVOKE_LEGAL_BASIS` з результатом відмови в аудиті.

### TC-N10.2 Інший Provider або неіснуюча підстава · P1 · авто
- **Очікуваний результат:** 404 з **однаковим** текстом «Legal basis not found» в обох випадках (рішення PO 8); `dataset_id` у відповіді немає.

### TC-N10.3 Повторне відкликання · P2 · авто
- **Очікуваний результат:** 409 «Legal basis is already revoked»; повторного `CONSENT_REVOKED` в аудиті немає (UC-14, EX1).
