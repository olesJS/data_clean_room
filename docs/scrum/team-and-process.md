## 2. Обґрунтування вибору методології

### Що таке Scrum

Scrum — це гнучка методологія, у якій робота ведеться короткими фіксованими ітераціями (спринтами). Кожен спринт починається плануванням і завершується оглядом результату та ретроспективою. Основні артефакти: Product Backlog (перелік усіх вимог), Sprint Backlog (задачі поточного спринту) та Increment (робоча частина продукту наприкінці спринту).

### Чому ми обрали Scrum

1. **Обсяг робіт відомий наперед.** Тема, вимоги методичних вказівок і перелік модулів системи визначені на початку, тому план можна розкласти на спринти із зрозумілою ціллю.
2. **Потрібні контрольні точки.** Методичні вказівки вимагають результат на кожному етапі (вимоги, SWOT, архітектура, прототип, тестування). Кожен спринт завершується демонстрацією, яка фіксує цей результат у звіті.
3. **Команда працює паралельно.** П'ять учасників одночасно ведуть аналітику, архітектуру, backend, frontend і тестування. Планування й щоденний обмін статусом допомагають вчасно виявляти залежності та блокери.
4. **Систематичне ведення задач оцінюється.** Scrum природно породжує беклог, спринти, нотатки зустрічей і ретроспективи, які потрібні для звіту.

### Чому не Kanban

Kanban доцільний, коли пріоритети мінливі, а задачі надходять потоком. У нашому проєкті термін фіксований, а обсяг відомий наперед, тому ми віддали перевагу ітераціям і зафіксованим цілям спринтів.

### Як ми адаптували Scrum

- Спринти тривають 2–3 тижні, а не стандартні 1–2: перший спринт складається з двох тижнів, середні з трьох, останній з двох.
- Щоденний Daily проводиться письмово в командному чаті (що зробив, що роблю, блокери). Окремо відбуваються короткі дзвінки.
- У спринтах по три тижні додатково проводиться проміжна перевірка (Mid-sprint check).
- Product Owner і Scrum-майстер одночасно виконують власні інженерні ролі, бо команда складається з п'яти осіб.

Вибір методології не змінюватиметься протягом проєкту без вагомих причин.

## 3. Організація роботи

### Інструменти

| Призначення | Інструмент |
| --- | --- |
| Беклог, спринти, дошка задач | Jira, проєкт «Data Clean Room» |
| Код і документація | GitHub, репозиторій `olesJS/data_clean_room` |

| UML-діаграми | draw.io або PlantUML |
| Щоденне спілкування | Месенджер Telegram |

### Події Scrum

| Захід | Коли | Тривалість | Результат |
| --- | --- | --- | --- |
| Sprint Planning | Перший день спринту | до 2 год (двотижневий) або до 3 год (тритижневий) | Ціль спринту і Sprint Backlog у Jira |
| Daily | Щодня письмово в чаті | 15 хв | Видимі блокери |
| Backlog Refinement | Щотижня | 45 хв | Оцінені історії наступного спринту |
| Mid-sprint check | Наприкінці другого тижня тритижневих спринтів | 30 хв | Перевірка Burndown, за потреби перенесення задач |
| Sprint Review | Останній день спринту | 1–1,5 год | Демонстрація виконаного |
| Retrospective | Одразу після Review | 45–60 хв | Нотатка за шаблоном Додатка Г |

Нотатки зустрічей, підсумки оглядів і ретроспективи зберігаються в `docs/scrum/` у файлах `sprint-N.md`.

### Правила дошки

- Стовпці дошки: To Do, In Progress, In Review, Done.
- Кожна задача має виконавця, оцінку в Story Points (шкала 1, 2, 3, 5, 8), епік і критерії приймання. Задача без виконавця в спринт не потрапляє.
- Не більше двох задач у статусі In Progress на одну людину.
- Задача переходить у Done лише після рев'ю іншим учасником.
- Блокер позначається прапорцем (Flag) у Jira з коментарем про причину.
- Нові ідеї проходять через Product Owner і потрапляють у наступний спринт. Склад поточного спринту змінюється лише за згодою Product Owner.

## 4. Definition of Done

Задача вважається виконаною, коли виконано **всі** умови нижче.

### Для коду

1. Робота ведеться в окремій гілці з ключем задачі Jira в назві, наприклад `feature/DCR-12-pii-regex`. Комітити безпосередньо в `main` заборонено.
2. Зміни потрапляють у `main` **лише через pull request**, у якому є **щонайменше одне схвалення (рев'ю) від іншого учасника команди**. Автор pull request не може схвалити його сам. Гілка `main` захищена: злиття без рев'ю неможливе.
3. Автоматична перевірка (CI) пройшла успішно: лінтер і тести зелені.
4. Для функціональності є автотест або описаний тест-кейс, що перевіряє критерії приймання.
5. Нова функціональність відповідає критеріям приймання із картки задачі в Jira.

### Для документів і діаграм

1. Артефакти додаються в репозиторій (`docs/`) також через pull request із рев'ю іншого учасника.
2. Діаграми зберігаються разом із вихідним файлом (draw.io або PlantUML), щоб їх можна було редагувати.

### Для всіх задач

1. Оновлено відповідну секцію звіту або документації.
2. У картці Jira вказано виконавця, оцінку та фактичний витрачений час, є посилання на pull request або документ.
3. Картка переведена в Done лише після проходження рев'ю (стовпець In Review).
4. Невиконані частини задачі винесено в окремі картки, а не залишено прихованими в Done.
