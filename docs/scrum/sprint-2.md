## 3. Мета Спринта 2

> Система розуміє вміст набору: показує профіль колонок, дефекти, Quality Score і PII-колонки з класом набору (Personal), працює на реальному API без mock. Аналітичні артефакти (нефункціональні вимоги, PEST/PRESTCOM, SWOT, Class Diagram) завершені.

**Що показуємо на Sprint Review (сценарій демо):**
1. Data Provider входить і завантажує `payroll.csv` (кейс 1).
2. Відкривається звіт профілювання: 500 рядків, 15 порожніх ІПН, 10 дублікатів, викиди в сумі, Quality Score.
3. Показано PII-колонки (`full_name`, `ipn`, `iban`) із типом, confidence і класом набору Personal.
4. Те саме для `customers.json` (кейс 2).
5. Правила якості (reject, flag) спрацьовують на дефектах, звіт про порушення доступний через API.

## 7. Sprint Review

**Мету спринта досягнуто частково, з застереженнями.**

Що показано (інкремент у `main`):
- профілювання колонок і API профілю (типи, пропуски, дублікати, викиди IQR), UI звіту профілювання на реальному API;
- PII-детектор (regex, контрольні суми, словники, назви колонок) з класом набору Personal, UI результатів PII з підтвердженням і виправленням типу;
- рушій правил якості в YAML і Quality Score: `payroll.csv` 91.8, `customers.json` 87.0;
- реєстр правової підстави (таблиця і API), права Data Steward;
- еталон PII, 92 автотести RBAC, 23 тест-кейси UC-03 – UC-05;
- Class Diagram, нефункціональні вимоги, PRESTCOM, SWOT, виправлені специфікації UC, макети наступних екранів.

Що не увійшло або має застереження:
- SCRUM-49 (UI правил і порушень) зроблено лише на боці frontend; API порушень перенесено в SCRUM-53 (Спринт 3).
- Знайдено дефект SCRUM-52: Data Consumer бачить неопубліковані набори (тест позначено `xfail`).
- У профілі немає показника `future_dates_count`, Alembic не підключено (зміни схеми потребують `docker compose down -v`), версії наборів (`dataset_versions`) потрібні для UC-06.
- PII-детектор знаходить 9 з 12 PII-колонок із нейтральними назвами; Product Owner прийняв це як обмеження прототипу.

Рішення Product Owner від 07.11 (узгоджено на рев'ю): Steward бачить метадані і замаскований профіль; базові показники Quality Score — пропуски і дублікати, викиди не штрафуються; `birth_date` — квазі-ідентифікатор; 404 для чужого або неіснуючого набору, 403 для заборони за роллю; події аудиту `PII_SCAN` і `VIEW_PII`.

## 11. Retrospective

Формат: Що пішло добре, Що не пішло, Що змінюємо. Пункти складено за даними Jira і GitHub, остаточно їх узгоджує команда на зустрічі.

**Що пішло добре**
- Виконано всі 19 задач, включно з 13 SP stretch.
- Сильна культура рев'ю: кожен PR отримав коментарі, частину дефектів (SCRUM-52, коди 403/404, назви подій аудиту) знайдено до злиття.
- Product Owner швидко ухвалював рішення (10 рішень від 07.11), що розблокувало frontend і тести.
- CI (ruff, pytest, lint і збірка frontend) ловив помилки до злиття.

**Що не пішло**
- Робота зосередилася в останні дні: до 05.11 не закрито жодної задачі, контрольну точку 04.11 пропущено.
- 25 SP закрито 09.11, після планового кінця спринта.
- Великий PR #18 об'єднав кілька задач і код інших учасників, що ускладнило рев'ю.
- Один коміт зроблено напряму в `main` без PR.
- Частину задач переведено в Done до злиття PR (SCRUM-32, SCRUM-38), що порушує Definition of Done.
- У назвах деяких PR вказано неправильні ключі Jira.
- Мета спринта не записана в полі Sprint goal у Jira.
- API для UI правил (SCRUM-49) не узгоджено заздалегідь, тому frontend зроблено без backend.
