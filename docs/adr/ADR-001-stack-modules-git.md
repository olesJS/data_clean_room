# ADR-001: Вибір стеку, структури модулів і правил роботи з Git

- **Статус:** Прийнято
- **Дата:** 23.10.2026
- **Задача:** DCR-23 / SCRUM-23
- **Автор:** Дмитро Петрунів (Роль C — Архітектор + Data Governance Engineer)

## Контекст

Команда з 5 осіб розпочинає розробку прототипу **Data Clean Room** —
інформаційної системи управління якістю та приватністю табличних даних.
На етапі Спринту 1 потрібно зафіксувати технологічний стек, архітектурне
розділення на модулі та правила роботи з Git, щоб:

- уникнути різночитань при паралельній розробці (5 людей, 2–3 тижні на спринт);
- забезпечити прозорий зв'язок між задачами в Jira та змінами в коді;
- зафіксувати обмеження MVP (прототип, а не production-ready).

## Рішення

### 1. Технологічний стек

| Шар              | Вибір                          | Обґрунтування |
|------------------|--------------------------------|---------------|
| Backend          | Python 3.11+, FastAPI          | швидкий старт, автогенерація OpenAPI, мінімум boilerplate для MVP |
| Обробка даних    | pandas                         | стандарт для табличних даних: профілювання, дублікати, викиди (IQR) |
| БД               | PostgreSQL + Alembic           | реляційна модель datasets/versions/audit_log, транзакції, JSONB |
| Frontend         | React (Vite)                   | швидкий dev-цикл, мінімум конфігурації |
| Правила якості   | YAML (PyYAML)                  | декларативні правила без змін коду |
| Діаграми         | draw.io / PlantUML             | безкоштовні, експорт у PNG/SVG для звіту |
| Макети           | Figma                          | безкоштовний план, спільна робота |

**Не обираємо:** Django (зайва адміністративна вага для MVP),
Flask (менше вбудованих можливостей для документації API),
NoSQL (не підходить для реляційної структури datasets/versions/audit).

### 2. Модулі системи

Backend ділиться на шість слабко зв'язаних модулів:

- `profiling` — профілювання колонок (тип, пропуски, унікальні, дублікати, викиди IQR)
- `quality` — рушій правил YAML, Quality Score, дії `reject` / `flag` / `block`
- `pii` — regex і словники для PII (email, телефон, ІПН, IBAN, картки, паспорт, ПІБ)
- `anonymization` — маскування, HMAC-хешування, узагальнення; lineage «оригінал → очищена»
- `governance` — класифікація, RBAC, реєстр правової підстави, publish gate, retention, audit log
- `api` — FastAPI-роутери, JWT-middleware, glue-шар

**Межі відповідальності:**

- Кожен модуль має публічний сервіс-інтерфейс, не імпортує внутрішні деталі інших.
- `api` — тонкий шар; бізнес-логіка тільки в модулях.
- `governance` є залежністю `api` і `anonymization` (перевірка прав), але не навпаки.

### 3. Правила роботи з Git

- **Гілки:** `feature/DCR-N-короткий-опис`, де `N` — номер задачі в Jira.
  Приклад: `feature/DCR-23-adr-stack-modules-git`.
- **Коміти:** англомовні, формат `DCR-N: короткий імперативний опис`.
  Приклад: `DCR-23: add ADR-001 for stack, modules and Git rules`.
- **Pull Request:** одна задача = один PR. У назві PR обов'язково `DCR-N` —
  це автоматично зв'язує PR із задачею в Jira (через GitHub for Jira).
- **Рев'ю:** мінімум одне схвалення іншого учасника перед merge.
- **`main`:** захищена (branch protection): заборонено прямий push,
  обов'язковий PR зі схваленням.
- **Merge strategy:** squash merge — одна задача = один коміт в історії `main`.

## Наслідки

**Позитивні:**
- Однаковий стек у всіх п'ятьох учасників.
- Прозора історія змін, зв'язок Jira ↔ Git працює автоматично.
- MVP легко запустити локально (`docker-compose`).

**Негативні / ризики:**
- FastAPI не дає готової адмінки — доведеться писати власні ендпоінти.
- Команда має бути знайома з FastAPI (ризик: хтось не знає — Budget 1 день на onboarding).

**Дії після прийняття:**
- D створює `docker-compose.yml`, CI (GitHub Actions), захист `main`.
- C налаштовує branch protection в GitHub.
- Усі дотримуються naming convention гілок і комітів.
